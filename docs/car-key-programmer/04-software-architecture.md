## 2. اختيار اللغات — والتبرير

| الطبقة | اللغة | لماذا هذه تحديدًا | لماذا ليس البدائل |
|---|---|---|---|
| **L1–L2 فيرموير** | **C (ESP-IDF)** | ESP-IDF هو C أصلًا؛ دعم كامل لـ TWAI و Secure Boot؛ لا مفاجآت في التوقيت | Rust على ESP32 ممكن لكن دعم الأجهزة الطرفية أقل نضجًا — مخاطرة غير مبرّرة في MVP |
| **L4–L5 نواة البروتوكول** | **Rust** | ISO-TP و UDS = تحليل بايتات + آلات حالة = **بالضبط حيث تقتل أخطاء الذاكرة**. Rust يمنعها وقت الترجمة. يُترجم لـ `.so/.dll/.a` ويُستخدم من Flutter و J2534 و Backend **بنفس الشيفرة** | C++ يعمل لكن بلا ضمانات؛ Dart بطيء جدًا ولا يصلح للتضمين في DLL؛ **نسخة واحدة من المنطق = نسخة واحدة من الأخطاء** |
| **L6–L8 التطبيق** | **Dart / Flutter** | تطبيق واحد لـ Android و iOS و Windows؛ دعم RTL ممتاز للعربية؛ سرعة تكرار عالية؛ FFI نظيف مع Rust | React Native: FFI أضعف مع Rust. Android أصلي: يضاعف العمل. Kotlin Multiplatform: أقل نضجًا لسطح المكتب |
| **L9 السحابة** | **Go** | ثنائي واحد، نشر بسيط، تزامن ممتاز، مناسب لخدمة OTA وسجلّ تدقيق عالي الإنتاجية | Node/TS بديل مقبول لو الفريق TS-first؛ Python مرفوض لطبقة التدقيق (أداء/أنواع) |
| **J2534 DLL** | **C++ (غلاف حول نواة Rust)** | مواصفة J2534 تُلزم واجهة C ABI في DLL على ويندوز | لا بديل — المواصفة تفرضها |
| **الأدوات الداخلية / تحليل البيانات** | **Python** | تحليل تسجيلات CAN، بناء ملفات تعريف المركبات، أدوات فريق الهندسة | مناسب تمامًا هنا فقط — **لا يدخل مسار المنتج** |

### القرار المعماري الأهم: **نواة Rust مشتركة**

```
                 ┌──────────────────┐
                 │  miftah-core     │  ← Rust: ISO-TP + UDS + OBD + ECU Scan
                 │  (crate واحد)     │
                 └────┬────┬────┬───┘
       ┌──────────────┘    │    └──────────────┐
┌──────▼───────┐   ┌───────▼──────┐    ┌───────▼────────┐
│ Flutter FFI  │   │ J2534 DLL    │    │ Cloud (Go/cgo) │
│ (تطبيق الفني) │   │ (ويندوز)     │    │ (محاكاة/اختبار)│
└──────────────┘   └──────────────┘    └────────────────┘
```
**لماذا يهم:** خطأ في تجميع ISO-TP يُصلَح مرّة واحدة ويستفيد منه الجميع.
المنافسون يعيدون كتابة هذا المنطق 3 مرّات ويعانون من اختلافات سلوك بين منصّاتهم.

## 3. تصميم الفيرموير (L1–L2)

### مهام FreeRTOS
| المهمة | الأولوية | الوظيفة |
|---|---|---|
| `can_rx_task` | 5 (أعلى) | استقبال TWAI → طابور دائري، بلا تخصيص ذاكرة |
| `can_tx_task` | 4 | إرسال مع مهلة، ومعالجة اكتمال الإرسال |
| `bus_monitor_task` | 4 | **مراقبة Bus-Off والتعافي** — تخفيف علّة TWAI المعروفة |
| `kline_task` | 3 | توقيت ISO 9141/14230 (5-baud init, fast init) |
| `host_link_task` | 3 | تأطير BLE/USB، CRC، تدفّق |
| `security_task` | 2 | ATECC608B، تحقّق الجلسة، تحديد المعدّل |
| `housekeeping` | 1 | قياس جهد البطارية، حرارة، LEDs، watchdog |

### قواعد صارمة للفيرموير
1. **لا تخصيص ذاكرة ديناميكي بعد الإقلاع.** كل المخازن ثابتة.
2. **Watchdog للأجهزة مفعّل دائمًا**، بمهلة 2 ثانية.
3. **وضع الاستماع فقط (Listen-Only) هو الافتراضي** عند الاتصال؛ الإرسال يتطلّب أمرًا صريحًا.
   → **حماية أساسية: لا نلمس ناقل السيارة قبل أن يقرّر المستخدم.**
4. **حدّ معدّل صارم**: لا أكثر من N إطار/ثانية نحو السيارة (قابل للضبط)، لمنع إغراق الناقل.
5. **مقاطعة فورية (Emergency Stop)** عبر أمر مخصّص وعبر انقطاع الرابط — أي فقد اتصال ⇒ توقّف الإرسال فورًا.
6. **قياس جهد البطارية إلزامي** قبل أي عملية طويلة.

### بروتوكول الرابط (Host ↔ Device)
```
┌────────┬──────┬──────────┬─────────┬──────────┬────────┐
│ 0xA5A5 │ VER  │ MSG_TYPE │ LEN(16) │ PAYLOAD  │ CRC32  │
│ 2 B    │ 1 B  │ 1 B      │ 2 B     │ 0..4096  │ 4 B    │
└────────┴──────┴──────────┴─────────┴──────────┴────────┘
```
أنواع الرسائل: `CONNECT`, `BUS_CONFIG`, `CAN_TX`, `CAN_RX`, `ISOTP_REQ`, `ISOTP_RSP`,
`KLINE_INIT`, `VBAT_READ`, `ATTEST_CHALLENGE`, `ATTEST_RESPONSE`, `ESTOP`, `FW_UPDATE_*`.

## 4. نواة Rust (L4–L5) — الوحدات

```
miftah-core/
├── src/
│   ├── link/           # واجهة مجرّدة للنقل (BLE/USB/محاكاة)
│   ├── isotp/          # ISO 15765-2: تجزئة، Flow Control، STmin، BS
│   ├── obd/            # SAE J1979 Modes 01–0A
│   ├── uds/            # ISO 14229: 0x10,0x11,0x14,0x19,0x22,0x27*,0x2E*,0x31,0x3E
│   ├── scan/           # جرد الوحدات، بصمة المركبة
│   ├── vin/            # فكّ VIN + خرائط WMI/VDS خاصة بتويوتا
│   ├── profile/        # تحميل ملفات تعريف المركبات (TOML/JSON موقّعة)
│   └── safety/         # حراسات: جهد، معدل، حدّ Security Access
└── tests/
    ├── fixtures/       # تسجيلات CAN حقيقية من مركبات اختبار
    └── fuzz/           # تشويش على محلّل ISO-TP (cargo-fuzz)
```

> `0x27` و `0x2E` موجودان في الواجهة **لأغراض التعرّف والرفض المُنظَّم فقط**:
> عند اكتشاف أن الإجراء يتطلب `Security Access`، تُرجع النواة الخطأ المُصنَّف
> `RequiresOemAuthorization` الذي تترجمه الواجهة إلى مسار OEM. **لا توجد أي محاولة حساب `Key`.**

## 5. الاختبار

| المستوى | الأداة | التغطية المستهدفة |
|---|---|---|
| وحدة (Rust) | `cargo test` + `proptest` | > 85% على `isotp`, `uds`, `vin` |
| تشويش | `cargo-fuzz` على محلّلات الإطارات | 24 ساعة/إصدار بلا انهيار |
| محاكاة مركبة | محاكي ECU برمجي (Rust) + `python-can` + `vcan` على Linux | كل حالات الأخطاء والمهلات |
| Hardware-in-the-Loop | لوحة اختبار: ESP32 + وحدات RAV4 مستعملة من التشليح | إجراءات كاملة بلا مركبة |
| مركبة حقيقية | أسطول اختبار / ورشة شريكة | قبول نهائي فقط |
| حقن أخطاء | فصل CAN، هبوط جهد، انقطاع BLE، Bus-Off | **لا يُفرج عن إصدار بلا اجتيازها** |

> 🔧 **استثمار موصى به بشدّة: مقعد اختبار من وحدات RAV4 حقيقية (Junkyard Bench).**
> تكلفة 400–900 USD، ويوفّر أسابيع من انتظار مركبات وسفر، ويسمح بأتمتة الاختبار في CI.
